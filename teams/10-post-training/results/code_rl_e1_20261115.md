# Code RL with objective_v1 on a 7B surrogate (E1), 15 Nov 2026

**Surrogate evidence, one seed.** Public Qwen2.5-Coder-7B-Instruct (Apache-2.0, dense), not the capstone model.
Every table below is one run with one seed. This report does not change the lead's `small_rl.md` or
`rl/objective_v1.*`; it records a separate experiment that uses the objective as written.

Drivers: `../rl-loop/pilots/fable_e1_20261115/` (README there). Evidence: `fable_20261115_evidence/`
(`summary_e1a.json`, `analysis_e1a.json`, `rescore_e1a.json`, `sample_e1a.json`, `reward_audit_trained_e1a.json`,
`screen_by_judge_e1a.json`, `error_kinds_screen_e1a.json`, `preflight.json`, `weights.json`). Per-problem scores,
task ids, completions and logs stay outside Git. The preregistration is a local file and is not in the repository.

## 1. Scoring speed: matched before/after (the PR run-gate evidence)

The reward stage was the bottleneck of the 15 Nov pilot. This is the matched comparison: the same 1,536 completions
(the E1 screen: 192 code_contests prompts x 8, saved on the volume), the same `stdio_check.score`, four settings.

- **Command:** `G10_E1_WORK=<private folder> modal run modal_app.py::rescore --run-id e1a --limit 1536`
  (from `rl-loop/pilots/fable_e1_20261115/`).
- **Hardware:** Modal CPU container, 32 cores requested (48 visible), 16 GiB; scorer process peak RSS 104 to 144 MB.
- **Timing boundary:** wall time of scoring all 1,536 completions only (data loading excluded), one run per setting.

| Setting | Scoring wall time | Passes | Rewards sha256 (first 8) | Matches the GPU job's rewards |
|---|---:|---:|---|---:|
| 8 threads, run all 20 tests (before: the 15 Nov pilot's path) | 603.5 s | 162 | 890f6c9c | 1,536 / 1,536 |
| 8 threads, stop at first wrong answer | 191.0 s | 162 | 890f6c9c | 1,536 / 1,536 |
| 32 threads, stop at first wrong answer | 232.7 s | 162 | 890f6c9c | 1,536 / 1,536 |
| 32 worker processes (`score_pool.py`), stop at first wrong answer (after) | **36.3 s** | 162 | 890f6c9c | 1,536 / 1,536 |

Final useful output lines (`fable_20261115_evidence/rescore_e1a.json`):

```
{"completions": 1536, "workers": 8,  "early_exit": false, "pool": false, "score_s": 603.47, "rewards_sha256": "890f6c9cd6bbe2f21f730332dbf67ee838072d19384c4fea8a05e13856c6c232", "passes": 162, "matches_gpu_job_rewards": 1536}
{"completions": 1536, "workers": 32, "early_exit": true,  "pool": true,  "score_s": 36.25,  "rewards_sha256": "890f6c9cd6bbe2f21f730332dbf67ee838072d19384c4fea8a05e13856c6c232", "passes": 162, "matches_gpu_job_rewards": 1536}
```

- 603.5 s to 36.3 s on identical input. The reward vector is byte-identical in all four settings (full sha256
  above) and equals the 1,536 rewards the GPU job computed.
- **Not byte-stable: the failure reason.** One or two programs flip between "runtime error" and "timeout" from run to
  run (error/timeout counts 455/28, 456/27, 455/28, 454/29). The reward does not depend on it. The full-result hash
  (reward, passed, total, reason) therefore differs between rows; only the reward hash is the contract.
- More threads did not help (232.7 s at 32 vs 191.0 s at 8): threads in one Python process are limited by the
  interpreter and by fork, not by cores.
- Inside the GPU job the same completions took 564.3 s with 32 threads and early exit, because every test forks from
  the trainer process (model, optimizer and sampler in memory). The pool's workers are started before the models
  load and stay small. Each worker gets its own slice of the sandbox uid range, because a uid's cleanup kills every
  process of that uid.
- Effect inside E1, same step shape (16 prompts x 8): reward stage 115.5 s and 109.0 s per step with threads (steps 1
  and 2 of the first call) against a mean of 15.7 s over the 60 steps with the pool; whole step 156 to 171 s against
  a mean of 50.4 s. Those steps sampled different completions, so this is the job-level effect, not the matched
  comparison (the table is the matched one).

Code: `rl-data/stdio_check.py` (early exit for the local runner, `set_uid_range`; `G10_STDIO_EARLY_EXIT=0` restores
the old path), `rl-data/score_worker.py`, `rl-loop/score_pool.py`, `train.reward_pool`. Tests:
`rl-loop/test_score_pool.py`, `rl-data/test_rl_data.py`.

Not measured: Docker-mode scoring (unchanged; early exit applies to the local runner only), other task families,
repeat timings of each setting.

## 2. Setup of the learning run

- Model Qwen2.5-Coder-7B-Instruct @ `c03e6d35`; trainable: attention weights only (822,212,608 parameters, fp32
  masters). objective_v1 (`tr_epsilon` 0.2, no reference KL, as in the contract), AdamW lr 1e-5, 16 prompts x 8
  samples per step, 1,024 new tokens, temperature 1, one epoch, 60 steps, vLLM 0.32.0 sampler.
- Data: RL data v1 code_contests. 192 train candidates screened, 56 mixed (10.55% pass rate) form the cohort.
  Held-out: 96 prompts, never filtered, 8 samples each. Train cohort re-evaluated with fresh samples x 8.
- Hardware: NVIDIA A100 80GB PCIe (Modal); torch 2.13.0+cu130, transformers 5.19.0, vllm 0.32.0 in the job image.
- Command (from `rl-loop/pilots/fable_e1_20261115/`, final form):
  `G10_E1_WORK=<private folder> G10_E1_CAP_USD=22 modal run --detach modal_app.py::e1 --run-id e1a --steps 60 --budget-s 3000 --grace-s 600 --max-calls 2`
- Call history: the first call was stopped on purpose after the step-0 evaluations to switch to the scorer pool; one
  relaunch failed in 3 minutes because the state identity had gained a `dt` key (fixed: the key is present only for
  DT runs); the run then resumed from the step-0 state, paused at its deadline at step 40, and the next call resumed
  and finished. Final state 9.87 GB written in 16.8 s.

## 3. Result

| Step | Held-out, 96 unfiltered prompts x 8 | Train cohort, 56 prompts x 8 (fresh samples) |
|---:|---:|---:|
| 0 | 0.151 | 0.299 |
| 10 | 0.238 | 0.645 |
| 20 | 0.253 | 0.768 |
| 30 | 0.242 | 0.839 |
| 40 | 0.242 | 0.884 |
| 50 | 0.243 | 0.926 |
| 60 | **0.251** | **0.944** |

*Surrogate model, one seed. Paired bootstrap over problems, 10,000 resamples (`analysis_e1a.json`).*

- **Primary endpoint (held-out, step 0 to 60): +0.100, 95% CI [+0.063, +0.142]**, 31 problems up, 3 down.
- Secondary (train cohort): +0.645, CI [+0.571, +0.714], 55 of 56 problems up, none down.
- Held-out by judge: Aizu +0.089 [+0.043, +0.140] (49 problems), HackerEarth +0.114 [+0.044, +0.195] (34), CodeChef
  +0.111 [0.000, +0.264] (9, interval touches zero), AtCoder 4 problems (not tested).
- 11 of the 68 held-out problems that were 0/8 at step 0 have at least one pass at step 60.

Final useful output (`summary_e1a.json`):

```
"heldout_change": {"problems": 96, "start": 0.151, "end": 0.2513, "diff": 0.1003, "ci_low": 0.0625, "ci_high": 0.1407, "ci_excludes_zero": true, "resamples": 10000}
"steps_with_optimizer_update": 60, "group_kinds_total": {"all_one": 495, "all_zero": 47, "tied_other": 0, "singleton": 0, "mixed": 418}
"peak_gpu_memory_gb": 58.05, "status": "COMPLETE", "resumed_from_step": 40
```

**Shape of the curve.** The whole held-out gain was there by step 10 (+0.087). For the next 50 steps held-out stayed
between 0.242 and 0.253 while the cohort rose from 0.645 to 0.944: after step 10 the run fits its 56 prompts. Kept
(mixed) groups per step fell from 12.6 in the first ten steps to 3.0 in the last ten, because most groups had become
all-pass (495 all-pass groups dropped over the run against 418 mixed).

**What the held-out gain consists of** (share of the 768 held-out completions; surrogate, one seed):

| | Step 0 | Step 60 |
|---|---:|---:|
| pass | 15.1% | 25.1% |
| runtime error | 31.5% | 21.4% |
| no code block | 7.9% | 3.3% |
| timeout | 3.9% | 9.2% |
| wrong answer | 41.5% | 41.0% |

Wrong answers did not move. The gain is programs that now run, plus fewer replies without a code block, partly
offset by more timeouts. On the trained cohort wrong answers did fall (44.9% to 3.1%).

Runtime errors before training (`error_kinds_screen_e1a.json`, 400 of the 1,374 failing screen completions, each run
on its first test in a locked-down local container): wrong answer 193, passes the first test but fails a later one 45,
SyntaxError 39, no code 36, TypeError 14, NameError 13, IndexError 13, ValueError on `int()` or unpacking 14,
timeout 7, others 26. No single input-format mistake dominates. What the syntax errors are was not examined.

**Mechanics.** Trust-region mask inert throughout (masked fraction at most 9.4e-4; sampler K3 1.5e-4 to 3.1e-4).
Stored-update share at least 0.996 every step. Relative weight change 0.0018. Truncation under 1% after step 0.
Peak 58.05 GB. Mean step 50.4 s (rollout 12.1, reward 15.7, update 15.8). vLLM sync check passed
(zeroed-unsynced K3 3.67, synced 0.0070, restored 0.00023).

## 4. The gain holds on tests the reward never used (R5b)

`rl-loop/sample_from_state.py` loaded only the sampler, pushed the step-60 state's trainable tensors into it, and
drew fresh samples with a new seed (held-out 96 x 8, cohort 56 x 8) from the base model and from the trained state.
`modal_audit.py::audit_trained` then ran every rewarded completion on 80 unused source tests (93 tasks, 7,440 tests,
all source hashes and kept-test prefixes verified).

- Commands: `modal run modal_app.py::sample --run-id e1a` (A100-80GB), then
  `modal run modal_audit.py::audit_trained --run-id e1a` (CPU), both with `G10_E1_WORK` set.

| | Base model | Step-60 state |
|---|---:|---:|
| Held-out, reward (20 kept tests) | 111 / 768 = 14.5% | 200 / 768 = 26.0% |
| Held-out, strict (kept + 80 unused tests) | 111 / 768 = 14.5% | **197 / 768 = 25.7%** |
| Cohort, reward | 143 / 448 = 31.9% | 427 / 448 = 95.3% |
| Cohort, strict | 140 / 448 = 31.3% | **411 / 448 = 91.7%** |
| Rewarded completions that fail an unused test | 3 / 254 = 1.2% | 19 / 627 = 3.0% |

*Surrogate model; one sampling seed per side; not a per-problem paired analysis.*

- The saved state reproduces the run's own evaluation through an independent sampler path and seed (run: held-out
  0.151 to 0.251, cohort 0.299 to 0.944). The checkpoint is usable, which the 15 Nov pilot never had.
- The held-out gain is not a reward artefact: under the stricter criterion it is 14.5% to 25.7%.
- False positives rose from 1.2% to 3.0% of rewarded completions (cohort 2.1% to 3.7%, held-out 0% to 1.5%): a small
  drift toward what the 20 tests miss, not the main source of the gain. Eight of the 19 are one AtCoder task's runtime
  errors and eight are HackerEarth wrong answers.

## 5. Observer: the surviving cohort is not the input mixture (R7)

E1 screen, 192 candidates x 8 (`screen_by_judge_e1a.json`; surrogate, one seed):

| Judge | Share of candidates | Share of kept (mixed) prompts | Pass rate |
|---|---:|---:|---:|
| Aizu | 49.5% | 23.2% | 4.7% |
| HackerEarth | 30.2% | 50.0% | 18.5% |
| CodeChef | 14.6% | 23.2% | 15.6% |
| AtCoder | 5.7% | 3.6% | 5.7% |

Failure reasons on the 1,536 screen completions: wrong answer 778, runtime error 456, pass 162, no code 113, timeout
27. The held-out set is 51% Aizu, so this cohort trains on a different mixture than the one it is evaluated on.
`train.py` now logs sampled and kept groups and kept tokens per subgroup at every step and in the summary. It was
added after E1 started, so E1's own steps do not carry it (the table is from the screen files); E4 is its first use.

## 6. Code added for this run (all in this PR)

`rl-loop/train.py`: `train.state_dir` durable state (atomic state files, `LATEST.json`, previous file kept),
append-only `evals.jsonl`, state written before each evaluation, deadline and `max_steps_this_call` pause,
finalize-only restart, train-cohort evaluation (`cohort_eval_k`), failure-reason counts, subgroup observer,
`reward_pool`, a temperature-1 guard for objective_v1 with the vLLM sampler, and `train.dt` (Deletion Tuning,
see `dt_rl_e4_20261115.md`). Without `state_dir` the old order of evaluation and metric rows is kept.
Tests: `test_resume_state.py`, `test_score_pool.py`, `test_sampler_branches.py`, `test_dt_rl.py`.
