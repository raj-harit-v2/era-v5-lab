```bash
.venv/bin/python teams/04-ke2/src/verify_frozen_table.py [PATH/raw_table_P32.npz]   # default: the committed p1536 table
```

The bf16 codes are built from the committed p1536 raw table, `results/tables/p1536-s0/raw_table_P32.npz` (0.8 MB).
Lab rule (15 Nov): a file above pr-guard's 5 MB limit is not committed; its build script, config and SHA-256 are.
So the 2 GiB bf16 matrix is rebuilt with `--materialize` (git-ignored) and checked against `matrix.sha256` in
`results/bf16/bf16_codes_P32.json`. `verify_frozen_table.py` checks any raw table, committed or rebuilt with
`build_tables.py --tokenizer <p1536 tokenizer.json> --pos-dims 32`, against `raw_table.sha256` there.

The tokenizer is never committed and never downloaded implicitly. Without `KE2_TOKENIZER` it is
looked up in the Hugging Face cache at the pinned revision (`src/ke2/config.py`), and every
table is bound to its `tokenizer.json` SHA-256 (`01d968a7…739fff`). `build_tables.py --allow-download`
fetches it when it is missing. The MPS step runs only where MPS is available.
`KE2_RUN_V1_MPS_TESTS=1` enables the MPS integration test, and `KE2_RUN_GPU_TESTS=1` the CUDA one.

For new Gate 3 work, use the frozen Team 3 p1536-s0 tokenizer with SHA-256
`e6b93a93a60520d7b1af2e9242485f443b5596a1e116b8f8798d83bbad25a64b` and the
tables in `results/tables/p1536-s0/`. Supply its local `tokenizer.json` explicitly to
`build_tables.py` or `revalidate_tokenizer_candidates.py`; neither script downloads it.
The earlier C3-s0 tokenizer has SHA-256 `15468e66…2ddc3` and its measurements remain a

`special_tokens_map.json` and `tokenizer_config.json` from merged Team 3 PR #407 beside its

### `decode_ref.py`: the reference decoder for G6

```python
from ke2.tables import ByteTable
from decode_ref import CodeTable, decode

table = ByteTable.load("teams/04-ke2/results/tables/raw_table_P32.npz", tokenizer_sha256=SHA)
result = decode(vectors, CodeTable.from_byte_table(table))   # vectors: (N, 256 * P), numpy or torch
result.token_ids, result.token_bytes, result.margins, result.sha256()
```

- **Input:** unprojected KE1 forward-codec vectors and a matching code table, which is a
  byte table plus the codec settings (the upstream defaults).
- **Output:** for each vector, the token ID, its raw bytes, the best cosine similarity, and the
  decode margin: the best minus the second-best cosine over the whole vocabulary.
- **Guarantees:** runs on CPU in float64 and is exhaustive (every token is scored). It is
  deterministic in the tested environment: matching outputs/hashes across tested query chunk sizes
  and a fresh process (format `ke2-decode-ref-v1`). Cross-platform bitwise equality is not asserted.
  Ties (margin 0) go to the lowest ID; zero query vectors are rejected.
- **CLI:** `python src/decode_ref.py --table <npz> --vectors <npy> [--out decoded.jsonl]` prints the hash.

It is meant to be slow and obviously correct. Each score uses the two-valued structure of the
codes (Lemma 1), so it gathers L values per token instead of doing a dense V × D product. The test
checks this against dense float64 codes. The existing correctness run uses 4,096 query IDs
against all 131,072 candidates at P=32 and P=64; its margins cover the full vocabulary.
Raw tables return original token bytes. Decode-text tables return stored text bytes, which may
already have lost partial UTF-8 information. The approximate chunk budget covers scoring
temporaries, not total process memory. See [decode_ref.md](decode_ref.md) for the reproducible
CPU comparison and why the structured cosine implementation is retained.

### Notes

- **Truncation rules.** The decode table cuts long tokens by stepping back over continuation
  bytes, and the raw table cuts plain bytes. The proofs use upstream's `utf8_safe_truncate`
  (`src/ke2/truncation.py` names all of them). No BrahmicTokenizer-131K token is longer than 32 bytes,
  so none of the rules ever cuts at P = 32 or 64. Revisit this when the tokenizer changes.
- **Tables** are saved as compressed `.npz`. Their content hash covers the arrays, not the file,
  so it matches #7's manifest.
